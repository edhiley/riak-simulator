# Plan

The simulator is built up in small steps from an interactive core. Each step adds one learning objective. The visual and writing rules are in [`web/DESIGN.md`](web/DESIGN.md).

## The page

- **Layout.** A header row holds the button that hides or shows the left column, the name, Play or Pause, the clock, the speed, the explainer links (History, Partitions, CAP theorem, How it works), Settings (a popover), the theme and a link to the source code. On a wide window the page fills the window and does not scroll.
- **Left column.** Four tabs: Requests, Traffic, Data and Scenarios. A green dot on a tab shows that its traffic still runs. When the column is hidden, a rail of tab icons stays, and an icon opens the column at that tab.
- **Cluster.** Nodes are cards in two rows, with a corridor between the rows. The clients wait on the left, and the load balancer sits in the middle. Add a node, What happened? and the cluster summary sit in the free top-left corner. The cards take the number of tile columns that makes the drawing largest in the space (`nodeGeometry` with `fit`).
- **Batch grid.** Write, read, delete and ping, by 1, 10, 100 or 1k. Reads and deletes use stored keys at random, so a count is off until enough keys are stored. A copy button gives an example curl command. Each batch is one summary line in the console, with a running count of the replies.
- **Traffic.** A steady rate (requests each simulated second) with a read and write mix, until stopped.
- **Scenarios.** Online shop at peak (mostly reads), live betting during a match (mostly writes; a node fails and comes back), likes and followers (data types). Each sets the traffic and the speed.
- **Clients.** Requests come from many clients, drawn as a fan of boxes. Each request leaves its client at its own moment (`Sim::submit_after`): a batch arrives at random times over about 2 seconds on screen, whatever the speed. So requests flow like independent clients, and do not arrive in one lump.
- **What happened?** Pauses the simulation and lists the steps of the last command: the last typed command, the last request of a batch, a data type button, a node start (hinted handoff) or a commit (partition moves). Each step is told from the side of the receiver: who gets what from whom, what it does next, and why.
- **Console.** A floating panel that opens from its button. Drag the title bar to move it, and the corner to resize it. Dock puts it back.
- **Settings.** Nodes (1 to 8), partitions (8 to 64), the quorum defaults (R, W, DW, PR and PW) and the timing. A change to nodes or partitions starts a new cluster with no data.
- **Explainers.** History, Partitions (the hash ring), CAP theorem (the "pick two" triangle and a network split) and How it works (the architecture, the sources and the licence). History dates are from sources checked on 25 November 2026.
- **Tiles and keys.** Each partition is a tile in its node's colour: the partition number, a dotted line, then a dot for each key the vnode stores (a dotted circle when it is empty). Dots shrink and move to fit as keys arrive. Point at a dot to see its key and value: the tiles with a copy get an outline, everything else dims, and the tooltip lists the partitions. Past 20 keys, or when dots would be too small to see, the tile shows a filled block. A key with siblings has a red ring.
- **Messages.** Pulses in the colour of the node that sent them, with a fading wake. A message that arrives leaves a fading streak and a ring at its target. Pulses from the clients and the load balancer are in the primary colour. There is no background traffic: every pulse comes from a request.
- **Ports and FSMs.** Checked in the 3.4.1 source. Each node card has a strip on its corridor edge: `:8098`, the HTTP listener (`web_port`), where client requests arrive and replies leave; the FSMs in the middle (a square for each running get, put, delete or list keys FSM, or a count when there are more than 4); `:8099`, the handoff listener (`handoff_port`), where moving data arrives over its own connection, drawn dashed; and a small notch where FSM commands from other nodes arrive over Erlang distribution, addressed to each vnode's proxy (`riak_core_vnode_proxy:reg_name/3`). The port text uses its own token, `--type-port`, because the drawing is scaled down. Not drawn: the Protocol Buffers port (8087) and the vnode proxies themselves.
- **Leveled, inside a vnode.** Checked in the 3.4.1 source (`leveled` and `riak_kv_leveled_backend`). Each vnode keeps a model of its leveled store (`core/src/leveled.rs`). The Inker appends each object to the active journal file. The Bookie keeps the key in its ledger cache (`leveled.cache_size`) and gives full caches to the Penciller's memory (`penciller_cache_size`). A full memory becomes one level 0 SST file, which the Penciller's clerk merges into level 1. A level over its file limit (4, 16, 64, ...) has a random file merged down (`mergefile_selector`). Journal files roll at `journal_objectcount`. The Inker's clerk then scores runs of up to 4 older files against a target from 25% to 75% (`score_run`) and compacts the best. Every count is the default divided by 1,000. Merges and compaction take no simulated time. A HEAD reads only the ledger; a GET also reads the journal. List keys reads only the bucket's range (`book_keylist` with a bucket). The release default backend is bitcask; the simulator models leveled only.
- **Characters.** Select a partition tile to open its store. The doorman (`riak_core_vnode_proxy`: the mailbox against the soft limit of 50 and the overload threshold of 10,000; shown, not enforced), the Bookie, the Inker, the Inker's clerk, the Penciller and the Penciller's clerk are 24 by 24 pixel characters. Each works while it does a step, and has a "Why?" for how it works. Movers carry each handoff message between vnodes. The FSMs stay as squares, because a character was too busy at that size. `web/scripts/draw-characters.py` writes `web/src/lib/characters.ts`; the colours are the `--pix-*` tokens, the same in both themes, on a paper stage.

## Behaviour

- **Siblings (from riak-emu).** Every created bucket type except `counters` and `sets` has allow_mult; the default type does not. A write with the vclock it read (X-Riak-Vclock) replaces the values that vclock has seen. A write with no vclock replaces nothing, so the values become siblings. Each vnode writes with its own dot, and copies merge by keeping every value the other copy has not seen. A read fetches from every vnode whose vclock no other answer includes and merges them, then replies 300 Multiple Choices with "Siblings:" and the vtags, or a multipart body with Accept: multipart/mixed, or one sibling with ?vtag=. The vclock header is a simulator encoding, not Riak's binary term. Not modelled: siblings in the default bucket type (Riak keeps the newest by timestamp there, as the simulator does), sibling explosion limits, and read repair. The Siblings card writes milk and bread with no vclock, reads, and resolves by writing the values back as one with the vclock.
- **Data types (CRDTs).** Bucket types `counters` and `sets` exist, as an operator would create them. `POST /types/<type>/buckets/<b>/datatypes/<k>` with `{"increment": n}`, `{"decrement": n}`, `{"add": x}`, `{"add_all": [...]}`, `{"remove": x}` or `{"remove_all": [...]}`; GET returns Riak's JSON. As in `riak_kv_crdt`: the coordinating vnode applies the update with its own id as the actor, other copies and handoff merge, and a read fetches from every vnode whose vclock no other answer includes and merges them. The counter is `riak_dt_pncounter`; the set is `riak_dt_orswot`. Not modelled: maps, registers, flags and HyperLogLog. The set context is a simulator encoding. Removing an element that a copy has not seen is ignored, where Riak returns a precondition error.
- **List keys.** `GET /buckets/<b>/keys?keys=true` (or `keys=stream`, which returns the same in one reply). The coordinator makes a coverage plan as `riak_core_coverage_plan` does: every Nth usual vnode on a running node, from an offset set by the request, then others where a node is stopped, so that every key range is answered once (11 of 32 vnodes on 5 nodes). Each vnode folds in its worker pool (`async_folds`), so it still answers other requests. It reads the bucket's keys from its leveled ledger at `fold_key` per key, and sends chunks of up to 100 keys (`key_buffer_size`). The coordinator merges them and replies with JSON. Too many stopped nodes give 503. A folding vnode has a moving dashed edge.
- **Sloppy quorum, PR and PW.** With one node running, writes still succeed: every copy goes to a fallback vnode on that node, as `riak_core_apl` allows. PR (primary read) and PW (primary write), 0 by default, refuse a request when fewer copies are on their usual vnodes, with 503 and Riak's body, `PW-value unsatisfied: got/wanted`. The simulator checks them at the node that takes the request; Riak checks them in the put and get state machines.
- **Stopping and starting.** A node can stop or start at any time, from its card or with `node3$ riak stop`. A stopped node takes no new work and finishes what it already has, so no request waits for ever. A crash in the middle of a request is not simulated. Requests use `riak_core_apl:get_apl_ann/3`: usual vnodes on running nodes, then a fallback vnode for each partition on a stopped node, on the next running owner after the first N partitions. The load balancer skips a stopped node; a direct request to it is refused. A started node keeps the copies it had. Then each fallback vnode that kept copies for it hands them back (hinted handoff), when the fallback vnode is idle and both nodes are running. The usual vnode keeps the newer version of each object by vclock, and the fallback vnode deletes the copies it sent. In Riak, handoff starts after the fallback vnode has been idle for `vnode_inactivity_timeout` (60 s by default); the simulator starts it at once. When neither vclock includes the other, Riak merges the versions; the simulator keeps the handed-off one.
- **Joining and leaving.** `nodeN$ riak admin cluster join nodeM`, `cluster leave [nodeM]`, `cluster plan` and `cluster commit`, as in Riak: changes are staged, the plan shows the moves, and commit applies them. "Add a node" and the leave button on a card run that sequence in the console. A node keeps its number and colour; a new node takes the lowest free number (up to 8). Partitions move by ownership handoff, at most 2 at a time for each node (riak_core `transfer_limit`). The old owner sends its objects to the new owner's copy, keeps answering requests, sends again only the objects written meanwhile, and the owner changes when both vnodes are idle. The new owner saves each handed-off object as a plain backend write (20 µs), not a whole put. A move waits while either node is stopped. A leaving node goes once it owns nothing and holds no copies for stopped nodes; a stopped node cannot leave. One change at a time: commit refuses while partitions still move.
- **Claim on join and leave.** The simulator's own claim, not Riak's. A joining node takes partitions from the nodes with the most; a leaving node's partitions go to the nodes with the fewest; then swaps repair any 3 neighbouring partitions not on 3 nodes. Where that cannot work, it takes a fresh layout and names its nodes to keep as many owners as possible. Tests check that the share stays equal and that the 3-nodes rule holds wherever a fresh ring of that shape has it.
- **Long runs.** The core forgets finished requests that no message refers to, and hands arrived messages to the page (`take_hops`) so it can draw them after they are gone.

## Decisions

- **Actors and messages (24 November 2026).** Nodes and vnodes are actors. Each vnode has a mailbox. Messages travel on a simulated network on a simulation clock. Every drawing shows something the core did; nothing is decoration.
- **Source first.** Request paths follow the OpenRiak 3.4.1 source, read from the `real-riak:3.4.1` image under `/home/riak/riak/_build/default/lib/`. The simplifications are listed at the top of `core/src/sim.rs`.
- **Overlay where real logic is too large.** Storage internals can be scaled down or drawn as an overlay when the real logic would be too much for small amounts of data. The page says when it does this.
- **No timeouts.** Requests have no timeout. Riak's default PUT timeout is 60 seconds.
- **Load balancer.** `localhost` in a command is a load balancer in front of the nodes. It sends each new request to the next node in turn (round robin), starting at a node chosen from the cluster's seed. `node1` to `node8` reach a node directly.
- **Timing.** Realistic timing is the default: a message between nodes takes 0.5 ms, a client message 1 ms, a put 1 ms, a HEAD 0.2 ms and a GET 0.3 ms. Even timing (every message and vnode action 0.5 ms) makes steps easier to follow. The speed is a fraction of real time, 1/4000 to 1×; the default is 1/1000.
- **Partition owners.** Each node gets an equal share, and any 3 neighbouring partitions are on 3 different nodes where possible, so a key's copies are on 3 nodes. Riak's claim algorithm has the same aim; the exact owners can differ.
- **riak-emu: not reused (25 November 2026).** Making riak-emu the vnode store would need a refactor (an I/O-free library, vector clocks with many actors, a merge for copies from other vnodes). The simulator keeps its own engine, and features are copied across from riak-emu one at a time when wanted, checked against the same OpenRiak source.
- **No lessons (26 November 2026).** The simulator is the product. Guided lessons were removed; the explainers, "What happened?" and the "Why?" texts do that work.
- **Writing.** Simplified technical English. See DESIGN.md.

## Not checked against the source

- **Forward target.** Riak forwards to the first replica vnode that answers the mailbox check below the soft limit. The simulator forwards to the owner of the first replica and does not show the check.
- **GET fetch.** `riak_kv_get_core` returns the vnodes to fetch the value from. How it chooses them has not been read. The simulator fetches from one vnode with the newest vclock.
- **Replay.** The core records every outside input with its time (`Sim::inputs`), but replay is not built. A replay must also record how many actions had run, because several actions can share one time.
