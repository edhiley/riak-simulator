# Plan

The simulator is built up in small steps from an interactive core. Each step adds one learning objective. Visual and writing rules are in [`web/DESIGN.md`](web/DESIGN.md).

## v3 (25 November 2026)

v2 (`../riak-sim-v2`) is parked as a checkpoint. v3 is the simulator only, with no lessons.

- **Layout.** Left: make traffic (batch grid, traffic, data types, scenarios). Right: the cluster, with "Add a node" and "What happened?" above it and stop, start and leave links on each node card.
- **Batch grid.** write, read, delete and ping, by 1, 10, 100 or 1k. Reads and deletes use stored keys at random, so a count is off until enough keys are stored. A copy button gives an example curl command. Each batch is one summary line in the console with a running count of the replies.
- **Traffic.** A steady rate (requests per simulated second) with a read and write mix, until stopped. The page shows the rate on screen at the current speed.
- **Scenarios.** Online shop (read-heavy), live betting (write-heavy, a node fails and returns), likes and followers (data types). Each sets the traffic and runs at 1/250 speed.
- **What happened?** Pauses the simulation and lists the steps of the last command: the last typed command, the last of a batch, a data type button, a node start (hinted handoff) or a commit (partition moves).
- **Quorum defaults.** R, W, DW, PR and PW in Settings apply to every request that does not set its own.
- **History.** A popup: the Dynamo paper, Basho and Riak, bet365 and NHS Digital, OpenRiak, and how Riak, DynamoDB and Cassandra differ. Dates are from sources checked on 25 November 2026.
- **Console.** A floating panel that opens only from its button. Drag the title bar to move it, the corner to resize it; Dock puts it back.
- **Siblings (from riak-emu).** Every created bucket type except `counters` and `sets` has allow_mult; the default type does not. A write with the vclock it read (X-Riak-Vclock) replaces the values that vclock has seen; a write with no vclock replaces nothing, so values become siblings. riak-emu's single-actor rule is extended to many actors (each vnode writes with its own dot), and copies merge by keeping every value the other copy has not seen. A read fetches from every vnode whose vclock no other answer includes and merges them, then replies 300 Multiple Choices with "Siblings:" and the vtags, or a multipart body with Accept: multipart/mixed, or one sibling with ?vtag=. The vclock header is a simulator encoding, not Riak's binary term. Not modelled: siblings in the default bucket type (Riak keeps the newest by timestamp there, as the simulator does), sibling explosion limits, and read repair. The Siblings card writes milk and bread with no vclock, reads, and resolves by writing the values back as one with the vclock; a key with siblings has a red ring on its dots.
- **List keys.** `GET /buckets/<b>/keys?keys=true` (or `keys=stream`, which returns the same in one reply). The coordinator makes a coverage plan as `riak_core_coverage_plan` does: every Nth usual vnode on a running node, from an offset set by the request, then others where a node is stopped, so that every key range is answered once (11 of 32 vnodes on 5 nodes). Each vnode folds in its worker pool (`async_folds`), so it still answers other requests: as with bitcask, the 3.4.1 release default, it reads every key it holds, in every bucket, at `fold_key` per key (10 µs even, 5 µs realistic), and sends chunks of up to 100 keys (`key_buffer_size`) spread over the fold. The coordinator merges them and replies with JSON. Too many stopped nodes give 503. Not modelled: leveled, which folds one bucket's range only, and the cost of the fold on the disk. A folding vnode has a moving dashed edge.
- **Clients.** Requests come from many clients, drawn as a fan of boxes. Each request leaves its client at its own moment (`Sim::submit_after`): a batch arrives at random times over about 2 seconds on screen, whatever the speed, and traffic at random times within each slice of simulated time. So requests flow, like independent clients, rather than arriving in one lump.
- **Leveled, inside a vnode.** Checked in the 3.4.1 source (`leveled` and `riak_kv_leveled_backend`). Each vnode keeps a model of its leveled store (`core/src/leveled.rs`): the Inker appends each object to the active journal file; the Bookie keeps the key in its ledger cache (`leveled.cache_size`) and gives full caches to the Penciller's memory (`penciller_cache_size`); a full memory becomes one level 0 SST file, which the Penciller's clerk merges into level 1; a level over its file limit (4, 16, 64, ...) has a random file merged down (`mergefile_selector`). Journal files roll at `journal_objectcount`; the Inker's clerk then scores runs of up to 4 older files against a target from 25% to 75% (`score_run`) and compacts the best. Every count is the default divided by 1000; merges and compaction take no simulated time. A HEAD reads only the ledger; a GET also reads the journal. List keys reads only the bucket's range (`book_keylist` with a bucket). Select a partition tile to open its store: the Bookie, the Inker, the Inker's clerk, the Penciller and the Penciller's clerk are pixel characters that work when they do a step. The release default backend is bitcask; the simulator models leveled only.
- **Characters.** 24 by 24 pixel sprites with a full palette (`web/scripts/draw-characters.py` writes `web/src/lib/characters.ts`; colours are the `--pix-*` tokens, the same in both themes, on a paper stage). Inside a vnode: the doorman (`riak_core_vnode_proxy`: the mailbox against the soft limit of 50 and the overload threshold of 10,000; shown, not enforced), the Bookie, the Inker, the Inker's clerk, the Penciller and the Penciller's clerk. Around the vnodes: movers carry each handoff message. The FSMs stay as squares in each node's strip (a sprite was too busy at that size). Each character has a "Why?" for how it works, and every leveled step carries its own why.
- **Ports and FSMs.** Checked in the 3.4.1 source. Each node card has a strip on its corridor edge: `:8098`, the HTTP listener (`web_port`), where client requests arrive and replies leave; the FSMs in the middle (one chip per running get, put, delete or list keys FSM, or a count when there are more than 4); the port text uses its own token, `--type-port`, because the drawing is scaled down; `:8099`, the handoff listener (`handoff_port`), where moving data arrives over its own connection, drawn dashed; and a small notch where FSM commands from other nodes arrive over Erlang distribution, addressed to each vnode's proxy (`riak_core_vnode_proxy:reg_name/3`). A put that arrives at a node with no copy of the key is forwarded to a new put FSM on a node with one (`riak_kv_put_fsm:select_coordinator`). Messages between FSMs in the same row go out into the corridor. Not drawn: the Protocol Buffers port (8087) and the vnode proxies themselves.
- **Fitting the window.** On a wide window the page fills the window and does not scroll. Play, the clock, speed, the explainer links, Settings (a popover) and Theme share one header row. Add a node, What happened? and the cluster summary sit in the free top-left corner of the drawing. The cards take the number of tile columns that makes the drawing largest in the space (`nodeGeometry` with `fit`). The left column can be hidden with the button at the left of the header; it then shows a rail of tab icons, and an icon opens the column at that tab.
- **Layout.** The clients wait on the left; the load balancer sits in the middle of the nodes. The left column has four tabs (Requests, Traffic, Data, Scenarios), so each set of controls fits without scrolling. A green dot on a tab shows its traffic is still running. Icons come from Lucide (`@lucide/svelte`, pinned). The chrome uses Material 3 Tonal Spot from a violet seed; each operation has one colour role (writes tertiary, reads secondary, deletes error, pings primary).
- **riak-emu: not reused (25 November 2026).** Making riak-emu the vnode store would need a refactor (an I/O-free library, multi-actor vector clocks, a merge for copies from other vnodes). Decided against: the simulator keeps its own engine, and features are copied across from riak-emu one at a time when wanted (for example siblings, list keys or 2i), checked against the same OpenRiak source.

## Decisions (24 November 2026)

- **Two sites.** `../riak-sim` is the phase 0 checkpoint and is not changed. This folder is the new version.
- **Actors and messages.** Nodes and vnodes are actors. Each vnode has a mailbox. Messages travel on a simulated network on a simulation clock. Every drawing shows something the core did; nothing is decoration.
- **Small queues.** Queues stay small on purpose. The user controls the overall speed and can hold, release or slow one message. There is no background load.
- **Overlay where real logic is too large.** Failure, recovery and storage internals can be drawn as an overlay when the real logic would be too much for small amounts of data. The page says when it does this.
- **Source first.** Request paths follow the OpenRiak 3.4.1 source, read from the `real-riak:3.4.1` image under `/home/riak/riak/_build/default/lib/`. Simplifications are listed in `core/src/sim.rs`.
- **No timeouts.** A held message waits until it is released. Riak's default PUT timeout is 60 seconds; the lesson text says so.
- **Writing.** Simplified technical English. See DESIGN.md.
- **Load balancer.** `localhost` in a command is a load balancer in front of the nodes. It sends each new request to the next node in turn (round robin), starting at a node chosen from the cluster's seed. `node1` to `node8` reach a node directly.
- **Timing.** Even timing (every message and vnode action 0.5 ms) is the default, so steps are easy to follow. Realistic timing is an option. Speed is a fraction of real time, 1/4000 to 1×; the default is 1/2000, so a 0.5 ms hop takes 1 second.
- **Pause at each step.** By default the simulation stops after each step and the left box explains it in plain English, with the reason in the same block. Continue runs to the next step. Continuous playback is an option in Settings.
- **Node view is the main view.** Nodes are cards in two even rows, in clockwise order, with a corridor between the rows for the client, the load balancer and the key. Partitions (vnodes) are tiles in the node colour. Messages meet a card at the edge facing the corridor, so no line crosses another card. The hash ring is an explainer, opened with "What are partitions?". Messages for a vnode on another node travel through that node.
- **One step per arriving message.** Each step is told from the receiver's side: who gets what from whom, what it does next, and why.
- **Partition owners.** Each node gets an equal share, and any 3 neighbouring partitions are on 3 different nodes where possible, so a key's copies are on 3 nodes. Riak's claim algorithm has the same aim; the exact owners can differ.
- **Commands.** A lesson command has Run, which runs it at once, and Edit, which puts it in the command line. After Run, Run is off until the part changes, unless the part asks to run again. Green marks the next thing to do: Continue while a request runs, then Next part. Next part sits by the part letters, away from Run. Reset goes back to part A on a new cluster.
- **Live mode.** A second mode beside Lessons: the console, example-command buttons (write, read, delete, a burst of writes, ping) and a switch for each node. Playback is continuous with realistic timing at 1/1000. Messages are pulses in the colour of the node that sent them, with a fading wake; an arrived message leaves a fading streak and a ring at its target. There is no background traffic: every pulse comes from a command. Tiles are taller: the partition number, a dotted line, then a dot for each key the vnode stores (a dotted circle when empty). Dots shrink and move to fit as keys arrive. Hovering a dot shows the key and value and outlines its other copies. Past 20 keys, or when dots would be too small to see, the tile shows a filled block; hovering it gives the count. Data type buttons update and read a counter and a set.
- **Data types (CRDTs).** Bucket types `counters` and `sets` exist, as an operator would create them. `POST /types/<type>/buckets/<b>/datatypes/<k>` with `{"increment": n}`, `{"decrement": n}`, `{"add": x}`, `{"add_all": [...]}`, `{"remove": x}` or `{"remove_all": [...]}`; GET returns Riak's JSON. As in `riak_kv_crdt`: the coordinating vnode applies the update with its own id as the actor, other copies and handoff merge, and a read fetches from every vnode whose vclock no other answer includes and merges them (`riak_kv_get_core` head merge). The counter is `riak_dt_pncounter`; the set is `riak_dt_orswot`. Not modelled: maps, registers, flags, HyperLogLog; the set context is a simulator encoding; removing an element a copy has not seen is ignored, where Riak returns a precondition error.
- **Sloppy quorum and pw/pr.** With one node running, writes still succeed: every copy goes to a fallback vnode on that node, as `riak_core_apl` allows. The result says all copies are on one node. `pw` and `pr` (default 0) refuse a request when fewer copies are on their usual vnodes, with 503 and Riak's body, `PW-value unsatisfied: got/wanted`. The simulator checks them at the node that takes the request; Riak checks them in the put and get state machines.
- **Live bursts.** "Write N random keys" writes up to 500 new keys, spread over at most 3 seconds.
- **Joining and leaving.** `nodeN$ riak admin cluster join nodeM`, `cluster leave [nodeM]`, `cluster plan` and `cluster commit`, as in Riak: changes are staged, the plan shows the moves, and commit applies them. Live mode has "Add a node" and "Leave" buttons that run that sequence in the console. A node keeps its number and colour; a new node takes the lowest free number (up to 8). Partitions move by ownership handoff, at most 2 at a time for each node (riak_core `transfer_limit`): the old owner sends its objects to the new owner's copy, keeps answering requests, re-sends only the objects written meanwhile, and the owner changes when both vnodes are idle. The new owner saves each handed-off object as a plain backend write (20 µs), not a whole put, so a move takes about as long as its data needs. A move waits while either node is stopped. A leaving node goes once it owns nothing and holds no copies for stopped nodes; a stopped node cannot leave. One change at a time: commit refuses while partitions are still moving.
- **Claim on join and leave.** The simulator's own claim, not Riak's. A joining node takes partitions from the nodes with the most; a leaving node's go to the nodes with the fewest; then swaps repair any 3 neighbouring partitions not on 3 nodes. Where that cannot work, it takes a fresh layout and names its nodes to keep as many owners as possible. Tests check the share stays equal and the 3-nodes rule holds wherever a fresh ring of that shape has it.
- **Stopping at any time.** A node can stop or start at any time. A stopped node takes no new work and finishes what it already has, so no request waits for ever and there are still no timeouts. A crash in the middle of a request is not simulated. Lessons still stop and start a node only when no request is running, to keep each step clear.
- **Long runs.** The core forgets finished requests that no message refers to, and hands arrived messages to the page (take_hops) so it can draw them after they are gone.
- **Stopped nodes.** Lesson commands stop and start nodes, as an operator would: `node3$ riak stop`. There are no manual controls. A node can stop or start only when no request is running. Requests use `riak_core_apl:get_apl_ann/3`: usual vnodes on running nodes, then a fallback vnode for each partition on a stopped node, on the next running owner after the first N partitions. The load balancer skips a stopped node; a direct request to it is refused. A started node keeps the copies it had. Then each fallback vnode that kept copies for it hands them back (hinted handoff), when the fallback vnode is idle and both its node and the usual node are running: the usual vnode keeps the newer version of each object by vclock, and the fallback vnode deletes the copies it sent. A copy written to it during handoff stays, and goes in a later handoff. In Riak, handoff starts after the fallback vnode has been idle for `vnode_inactivity_timeout` (60 s by default); the simulator starts it at once. When neither vclock includes the other, Riak merges the versions; the simulator keeps the handed-off one.

## Not checked against the source

- **Forward target.** Riak forwards to the first replica vnode that answers the mailbox check below the soft limit. The simulator forwards to the owner of the first replica and does not show the check.
- **GET fetch.** `riak_kv_get_core` returns the vnodes to fetch the value from. How it chooses them has not been read. The simulator fetches from one vnode with the newest vclock.
- **Replay.** Inputs are recorded with their time, but replay is not built. A replay must also record how many actions had run, because several actions can share one time.
